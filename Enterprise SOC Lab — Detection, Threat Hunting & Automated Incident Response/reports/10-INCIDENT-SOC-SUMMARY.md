# 10-Incident SOC Investigation Summary

**Project:** Enterprise SOC Lab — Detection, Threat Hunting & Automated Incident Response  
**Environment:** Wazuh SIEM, Windows, Sysmon, Linux, Python SOC Automation  
**Incident Count:** 10  
**Overall Outcome:** All 10 investigations documented and closed  
**Classification:** Defensive security lab — controlled testing and investigation

---

## 1. Executive Summary

This report consolidates ten SOC investigations conducted in a controlled lab environment. The investigations covered Windows authentication anomalies, suspicious PowerShell execution, persistence mechanisms, outbound network behavior, Linux SSH brute-force activity, and process execution patterns.

The workflow included alert review, endpoint telemetry analysis, process and event correlation, IOC assessment, MITRE ATT&CK mapping, incident documentation, and response recommendations.

The investigations identified several opportunities to improve detection coverage, particularly around suspicious parent-child process relationships, outbound network events, and correlation of DNS and network activity with process execution.

**No real-world compromise was established by these investigations.** The tested behaviors were controlled lab validations or events assessed as benign based on the available evidence. Detection gaps are documented as opportunities for improvement, not as proof that an attack succeeded.

## 3. Incident Investigation Findings

### INC-001 — Multiple Windows Logon Failures

Repeated Windows logon failures were observed within a 240-second window, generating Wazuh rule 60204.

**Assessment:** The pattern was consistent with a brute-force detection scenario and was validated in the controlled environment.

**Disposition:** Medium severity; closed after investigation.

**MITRE ATT&CK:** T1110 — Brute Force.

### INC-002 — Failed Logons and Account Lockout

Repeated failed logons involved the Administrator account, followed by an account lockout. A later successful service logon event was reviewed separately rather than treated as proof that the earlier failures led to compromise.

**Assessment:** Authentication anomalies were identified and investigated. The subsequent service logon did not, by itself, establish unauthorized access.

**Disposition:** Medium severity; closed with the available evidence documented.

### INC-003 — Suspicious PowerShell Execution

Nested PowerShell execution was observed and associated with Wazuh rules 92027 and 92213.

**Assessment:** The activity was generated as a controlled lab validation. The investigation exercised endpoint alert review and PowerShell detection workflows.

**Disposition:** Medium severity; closed.

**MITRE ATT&CK:** T1059.001 — PowerShell.

### INC-004 — Encoded PowerShell

Sysmon Event ID 1 recorded an encoded PowerShell command, and Wazuh rule 92057 generated a high-level alert.

The command was decoded and found to execute a harmless `Write-Output` statement.

**Assessment:** Encoded command execution is worth investigating, but encoding alone does not prove malicious intent.

**Disposition:** Medium severity; closed after command review.

**MITRE ATT&CK:** T1059.001 — PowerShell.

### INC-005 — Document Application Spawning PowerShell

Sysmon recorded a process relationship in which `soffice.bin` spawned `powershell.exe`. The relationship did not generate a dedicated Wazuh alert under the tested configuration.

**Assessment:** The process chain warranted review because document applications launching shells can be suspicious. The lab evidence established the process relationship, not a successful compromise.

**Detection gap:** Improve detection of unusual parent-child process relationships, including office or document applications spawning scripting interpreters.

**Disposition:** Medium severity; controlled validation and detection gap documented.

### INC-006 — Scheduled Task Persistence

A temporary scheduled task named `Project--Persistence-Test` was created with a PowerShell action. Related Sysmon process telemetry and Wazuh rule 92213 were reviewed, and the test task was removed.

**Assessment:** The investigation exercised scheduled-task persistence analysis. The observed activity was part of a controlled test.

**Disposition:** Medium severity; closed after cleanup.

**MITRE ATT&CK:** T1053.005 — Scheduled Task.

### INC-007 — Suspicious Outbound Connection

Controlled PowerShell HTTPS activity to `example.com` was investigated. The expected Sysmon Event ID 3 network-connect event was not produced by the tested `Test-NetConnection` method under the current configuration.

**Assessment:** The investigation identified a telemetry-validation issue. The absence of the expected event means the test did not demonstrate that the current configuration captures every relevant connection attempt.

**Detection gap:** Validate Sysmon network-event collection and build process-to-network correlation for relevant outbound connections.

**Disposition:** Low / Informational; closed with the limitation documented.

### INC-008 — Windows Service Persistence

A temporary service named `Project-Svc` was configured with a PowerShell action. The service failed because `powershell.exe` does not implement the Windows service interface required by that configuration. The test service was removed.

**Assessment:** The service-creation behavior was investigated as a persistence technique. Successful service execution or successful persistence was not established.

**Detection opportunity:** Alert on unexpected service creation and suspicious service image paths or command lines, then validate the service's actual execution outcome.

**Disposition:** Medium severity; closed after cleanup.

**MITRE ATT&CK:** T1543.003 — Windows Service.

### INC-009 — Linux SSH Brute Force / Invalid User

Ten invalid-user SSH attempts were generated and investigated. Wazuh rules 5710 and 5712 provided relevant authentication telemetry. Legitimate `ubuntu` sessions from the known source were scoped out of the brute-force finding.

**Assessment:** The invalid-user attempts demonstrated the SSH authentication detection workflow. The presence of failed attempts alone did not establish a successful unauthorized login.

**Disposition:** Medium severity; closed with legitimate sessions distinguished from the test activity.

**MITRE ATT&CK:** T1110 — Brute Force.

### INC-010 — Possible C2-Like Behavior

A controlled PowerShell sequence generated DNS and HTTPS activity. Sysmon process creation, DNS, and network events were reviewed together. Wazuh rules 92027 and 92213 were present, but dedicated correlation of DNS and network events with the originating process was not established.

**Assessment:** The sequence resembled behavior worth investigating during threat hunting, but the lab evidence did not establish command-and-control activity.

**Detection gap:** Correlate process creation, DNS lookups, and outbound connections using process identifiers, timestamps, and endpoint identity.

**Disposition:** Low / Informational; closed as a controlled validation with the correlation gap documented.

## 4. Detection Engineering Review

The lab exercised existing Wazuh and Sysmon detections and identified areas for further tuning.

| Detection area | Finding | Recommended improvement |
|---|---|---|
| Authentication failures | Repeated Windows and Linux failures were observable | Tune thresholds and group activity by account, source, endpoint, and time window |
| PowerShell execution | PowerShell activity generated relevant alerts | Correlate command-line context, parent process, user, and related endpoint events |
| Encoded PowerShell | Encoded command was detected and decoded | Preserve decoded-command analysis and avoid treating encoding alone as proof of malware |
| Document-to-shell execution | Process relationship lacked a dedicated alert | Add and validate parent-child process detection |
| Scheduled task creation | Controlled persistence activity was investigated | Monitor task creation and suspicious task actions |
| Service creation | Test service behavior was investigated | Detect unusual service installation and validate execution results |
| Outbound network activity | Expected telemetry was not available for one test method | Validate Sysmon configuration and network event collection |
| DNS and network correlation | Related events were not fully correlated by Wazuh | Develop and test process-linked DNS/network correlation |

These are identified improvement areas. They should not be described as fixed until a rule or configuration change has been implemented and validated with positive and negative test cases.

## 5. Threat Hunting Summary

Five hunts were completed and documented:

1. **HUNT-001 — Windows Authentication Anomalies:** Reviewed authentication activity for repeated failures and unusual patterns.
2. **HUNT-002 — PowerShell Execution:** Investigated PowerShell process and command-line activity, including benign agent activity.
3. **HUNT-003 — Persistence Mechanisms:** Examined scheduled-task and persistence-related evidence; the tested task query did not return suspicious actions.
4. **HUNT-004 — Outbound Network Behavior:** Reviewed available network telemetry and identified benign processes and traffic alongside collection limitations.
5. **HUNT-005 — Process Tree Anomalies:** Examined parent-child process relationships for execution chains requiring further investigation.

The hunts documented both relevant findings and limitations. A hunt returning no suspicious results is not proof that the environment is free of threats.

## 7. Python SOC Automation and SOAR Validation

The automation workflow includes alert parsing, IOC extraction and enrichment, alert correlation, incident generation, response recommendations, and audit logging.

### Live Wazuh alert validation

A real Wazuh alert was processed from:

`/var/ossec/logs/alerts/alerts.json`

The validation selected rule `92213`, which reported an executable file dropped in a folder commonly used by malware. The evidence involved a PowerShell-related temporary script path associated with policy testing.

| Field | Result |
|---|---|
| Wazuh rule | 92213 |
| Reported rule level | 15 |
| Generated incident | INC-20261008-001 |
| Automation risk score | 2 |
| Automation severity | LOW |

The rule's Wazuh level and the automation's calculated severity are different fields produced by different systems. The high Wazuh rule level should not be confused with the automation's risk score.

The evidence was consistent with a PowerShell execution-policy validation artifact. The automation correctly retained an unreviewed status and did not label the event confirmed malware.

## 8. Incident Response Playbooks

The repository includes five playbooks:

- **PB-001 — Windows Brute Force**
- **PB-002 — Suspicious PowerShell**
- **PB-003 — Persistence**
- **PB-004 — Suspicious Network / C2**

The playbooks support a consistent workflow: validate the alert, collect relevant evidence, determine scope, assess impact, document findings, recommend containment or remediation when justified, and record closure.

Response actions should be authorized and proportionate to the evidence. In a production environment, destructive or disruptive actions require appropriate approval and safeguards.

## 11. Limitations and Next Steps

The project is a portfolio lab, not a production SOC deployment. The investigations do not establish that every attack path is detected or that every alert is correctly classified.

Recommended next steps:

1. Implement and validate dedicated detection for document applications spawning scripting interpreters.
2. Improve process-linked correlation of DNS and outbound network events.
3. Validate Sysmon network-event collection with multiple controlled test methods.
4. Add positive and negative tests for any new detection rules.
5. Review the Python automation's parsing and correlation behavior against representative alert formats.
6. Keep response actions in simulation or approval mode until safety checks and authorization controls have been tested.
7. Ensure the public repository contains sanitized evidence and no credentials, API keys, sensitive logs, or private infrastructure details.

## 12. Conclusion

This ten-incident lab demonstrates a practical SOC workflow across Windows and Linux authentication, PowerShell investigation, persistence analysis, network telemetry, threat hunting, IOC enrichment, Python automation, and incident reporting.

The most important outcome is not the number of alerts generated; it is the ability to connect telemetry to a defensible investigation, distinguish suspicious behavior from confirmed compromise, record limitations, and recommend evidence-based next steps.

**Final assessment:** Ten investigations documented and closed, five threat hunts completed, five playbooks available, core automation tests passing, and several detection improvements identified for future implementation and validation.
